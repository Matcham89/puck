Event-Driven AI: workflow, how it works, where it runs

An event becomes a reviewed draft PR. The LLM does only the judgment work; validation, publishing and routing are deterministic and cost no tokens.

1. End-to-end workflow (three boxes, as in the blueprint)

TRIGGER + QUEUE · NO LLM

Event, intake, queue, worker

  • A Jira webhook (/webhooks/jira, HMAC-verified) or POST /events
  • Intake parses the ticket (rich text to plain text), needs the trigger label, drops duplicates, and maps project + component to a service catalog entry
  • Bad input gets a 400; good input becomes canonical JSON
  • Job goes on a Redis queue; a small web UI (same pod) shows queue, stages, validator results and a live log
  • Worker pops it, fetches the repo brief, asks kagent

Gate: deterministic lint

  • Overlays the upload on a fresh clone of base
  • Rejects anything outside allowed paths

BOX C · PUBLISHER · NO LLM · GIT WRITE

Gate: publish

  • Only the worker may call it (key the agent never has)
  • Branch learn/<ticket>, chosen by code, never main
  • Commit, push, open a draft PR

↺ On any failure: the worker starts a fresh agent session (clean context, same cached brief) with the exact errors and the branch name. The agent restores its last upload, fixes only what was reported, and resubmits: up to 3 attempts. If it still fails the job is marked failed and nothing is published.

How it works: control, safety and cost

Why the agent can be trusted with a repo it can't push to, and why each run costs cents.

Step by step

  1. Event in. A Jira webhook is signature-checked, parsed (ADF description to text), matched to a service by project and component, and only acted on when the trigger label is added. Redeliveries and a second trigger while a job runs are ignored. Bad input is rejected before anything is queued.
  2. Queue. The canonical job (repo, base branch, allowed paths, instruction) is stored in Redis and queued. The worker is the only consumer.
  3. Brief first. The worker asks the gate for a deterministic repo brief (plugin index, tree, the repo's own rules) and puts it at the top of the message, so it caches across jobs.
  4. Agent run. kagent starts the actor on Substrate (gVisor). The agent downloads a snapshot, edits files, writes PR.md (title + reasoning), and runs one submit script that uploads only the changed files.
  5. Validation. The gate overlays the upload on a fresh clone, auto-fixes formatting, then lints the changed files. Failures return as text to the agent's own turn; if the turn ends unvalidated, the worker retries in a fresh session with the errors and branch name.
  6. Publish. The worker, holding the publish key, tells the gate to push the branch and open the draft PR.
  7. Done. The job status holds the PR URL; kagent suspends the idle sandbox, and a retry or new job starts clean.
Dry run: an event with "dry_run": true stops after step 5, so cost and behaviour can be measured without opening a PR.

Security model

RiskControl
Agent leaks a tokenIt never has one. The git token lives only in the gate pod; the LLM key lives only in the in-cluster gateway, which only the sandbox's egress path may reach.
Agent pushes or opens PRs itselfNo git, no network except two allowlisted origins. Publish needs a key only the worker holds.
Writes to mainBranch name is chosen by code (learn/*), explicit refspec, draft only.
Touches CI or unrelated filesAllowed paths from the catalog; anything else is rejected, unchanged files ignored.
Hostile ticket text (prompt injection)Capped, control characters stripped, labelled as data. The real defence is containment: no credentials, an egress allowlist, a gate, draft PRs.
Token in error textEvery message returned to the agent is scrubbed.
Bad change slips throughDeterministic lint (a per-service profile in the catalog), then human review of a draft PR.
Limit: egress rules work per origin, not per path, so the gate's publish route is protected by the worker-only key, not the network.

What's proven

  • Event to draft PR, hands-off, on the real repo (PRs #8, #9)
  • Simulated Jira: signed webhook, parse, queue, agent, comment back (dedupe, in-flight and trigger rules tested)
  • Cluster rebuilt from nothing with one script, first try
  • Sandbox reaches only the gateway and the gate
  • Lint failures loop back and recover (shellcheck caught, fixed, re-validated)
  • Fresh-context retries, tested with a stubbed agent and gate
  • Gateway in the cluster; a NetworkPolicy stops other pods (the gate holds the git token) from using the LLM key
  • E2E suite: 22 checks (k8s/tests/e2e.py, dry runs, ~$0.05 per agent job)
  • Cost down about 47% after the brief and fixes

Not yet

  • Infra repos: the Terraform/Helm/Kubernetes lint is tested on fixtures, not yet on a real infra repo
  • Skills from git: the agent's rules are inline; central skills could load on demand
  • Worker connect-retry when Redis starts late
  • Other clusters: the same manifests should work wherever Substrate and kagent run; only this kind setup is tested

Next

  • Point the Jira webhook at intake and JIRA_BASE_URL at real Jira (needs an API credential Secret); the simulator already exercises the same path
  • Add a first infrastructure repo to the catalog to try the Terraform / Helm / Kubernetes lint for real
  • Open item: the gateway has no auth of its own; the NetworkPolicy is its only guard
